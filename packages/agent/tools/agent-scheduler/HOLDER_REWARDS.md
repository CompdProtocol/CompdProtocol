Holder Rewards local integration

Live execution is disabled. The example deliberately contains no invented launch, contract addresses, or code pins. This is not deployment approval or independent clearance.

The canonical Kernel still allocates only 10% of positive realized strategy profit to Holder Rewards. No fee revenue, principal, Buyback Reserve or Protocol Reserve is substituted. Native payments debit the same reviewed leaf, reserve, window, liability and physical balance atomically. Failed transfers retain liabilities. Permissionless pay/retry and batches of at most ten cannot choose recipients or amounts. Candidate submission/materialization remain restricted to the existing finalizer; the 1,800-second review is unchanged.

Before a future activation, the existing administrator can configure one launch checkpoint with configureHolderLaunch(block, hash, timestamp). The contract authenticates a recent block hash (within 256 blocks); the timestamp and COMPD launch association are administrator attestations, not on-chain header/receipt proofs. Require the existing launch verifier plus matching indexer evidence before that call. Activation rechecks the hash. The legacy unconfigured eight-hour path is preserved for historical fixtures, but the new keeper rejects it for a launch-window workflow.

Epochs are half-open: [launch, launch+900), then [launch+900, next UTC eight-hour boundary) if nonempty, then UTC eight-hour windows. The shorter bridge explicitly accounts for the transition; it never overlaps or discards time. A closed zero-funded window finalizes idempotently without creating a liability or moving funds. Fresh-genesis strategy admission still requires activation, a pause and a 24-hour admission delay: do not manufacture a funded first/bridge epoch to bypass it.

The SQLite index begins at verified token creation, requires the prior block to have no token code, a successful canonical Portal launch receipt containing the mint, chain 56, timestamp/hash and runtime pins, and 18 decimals. It indexes raw Transfer/Kernel logs and corroborating receipts, verifies historical supply and changed balances, and reconciles all known balances at epoch boundaries. It persists atomic block checkpoints and rewinds to a common ancestor on reorg. RPC finalized state plus at least twelve confirmations are required; neither this policy nor one provider is independent BSC finality clearance. Token proxy/beacon upgrade authority and implementation provenance still require independent integration review.

Ranking retains the existing canonical threshold-at-accrual rule: integrate balance only during periods where it is at least 500,000 tokens; rank the resulting balance-time integrals, with numeric ascending address tie-breaking. Top thirty, Hamilton rounding, and exact conservation remain deterministic. Zero-wei allocations remain visible in rankings but are omitted from payable leaves. Explicit reviewed exclusions must cover every canonical protocol module; pool/router/fee-wallet exclusion policy and its consistency with the on-chain exclusion commitment require owner/finalizer review.

holder_keeper.py is a read-only, self-hosted loop, dry-run only. It reconstructs the epoch, generates deterministic candidate/evidence/Merkle proposals, preserves proposals across restart, observes materialization and the chain-timestamp review delay, and prepares unsigned finalization, payBatch or retry actions. Paid leaves are excluded, wrong-window leaves rejected, and the remaining liabilities must match the Kernel window pool. A proposal checkpoint reorg blocks progression; it never silently corrects an accepted candidate. No private keys, signing or broadcasting API exists in this worker.

The encoder reuses core.mjs's canonical hash/Merkle routines; the original production verification guards remain enabled. replaySourceHashes must match the five exact files listed in candidate_proposal(), and replayCodeHash must equal Keccak-256 of the compact, key-sorted JSON mapping of those SHA-256 hashes. These pins identify the source bundle; they are not an EVM replay-contract attestation. Authorized finalizer review remains necessary. Funded windows without eligible recipients are blocked for the existing empty-window evidence/recovery process, not assigned invented payees.

Future owner-executable read-only usage, after supplying genuine reviewed configuration:

    python holder_keeper.py --config holder-rewards.json --state holder-index.sqlite --once
    python public_status.py --config agent-config.json --identities identities.json --holder-config holder-rewards.json --holder-state holder-index.sqlite

BSC_RPC_URL stays server-side. COMPD_CAST_BIN and COMPD_NODE_BIN select the existing local binaries. No RPC URL or credentials are written to the frontend. The public API exposes only whitelisted observations; current ranks are a confirmed-event preview, payout totals cover all indexed Kernel payments, outstanding liabilities are read from canonical Holder State, and transaction links require confirmed indexed hashes. Manual Buyback authentication, Agent operation, economic percentages, styles and animations are unchanged.

Remaining launch gates: genuine reserved-token deployment/launch evidence; exclusion/implementation and finality review; source-bundle approval and finalizer identity; qualification of the newly compiled constructor-bound graph and pins; isolated automated signing/receipt execution qualification before separate live authorization. No external RPC was used in these tests. All historical failures, analyzer findings and nineteen partial-HR coverage dispositions remain unchanged and are not cleared by this patch.
